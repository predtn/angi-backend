# ANGI — Coding Rules

Rules every change to the backend code must follow. System facts and contracts: `project_architecture.md` (read its §0 first: the design documents decide, and a decision they do not contain is asked about, not invented). Git and pull requests: `commit_guide.md`.

## 1. Project structure

`<Module>` is one of `Auth`, `Account`, `Restaurant`, `Discovery`, `Roadmap`, `Social`, `Notification`, `Moderation`, `Administration`, `Audit` (`project_architecture.md` §1). `<Feature>` is one use case of that module (`Login`, `Refresh`).

```
ANGI.Domain/
  Common/                         BaseEntity, IHasCreatedAt, IHasUpdatedAt, ISoftDelete
  Entities/                       plain C# classes, no framework attributes
  Enums/                          business enums only

ANGI.Application/
  Common/
    Exceptions/                   AppException and BadRequest, Unauthorized, Forbidden, NotFound, Conflict, ServiceUnavailable (+ subclasses that carry extra data)
    Interfaces/
      Repositories/               IUnitOfWork, IUnitOfWorkTransaction; <Module>/I<Name>Repository
      Services/                   I<Name>Service, or <Area>/I<Name>Service when an area has several (Auth/, Recommendation/)
      UseCases/<Module>/          I<Feature>UseCase
    Models/                       Paged<T>, MediaUploadResult; <Module>/ for internal models (not API DTOs)
  DTOs/<Module>/                  request, response and shared DTOs (names: §3)
  UseCases/
    <Module>/<Module>Module.cs    Add<Module>UseCases() (§12)
    <Module>/<Feature>/           <Feature>UseCase
    <Module>/<Name>Mapper.cs      only for mapping shared by several use cases of the module
    Validators/<Module>/          <RequestDto>Validator
  DependencyInjection.cs          AddApplication()

ANGI.Infrastructure/
  Persistences/
    ANGIContext.cs
    Configs/                      one IEntityTypeConfiguration<T> per table
    Conventions/                  enum, timestamp and soft-delete conventions
    Migrations/                   generated by dotnet ef
    Repositories/                 UnitOfWork; <Module>/<Name>Repository
  Services/                       <Name>Service, or <Area>/ mirroring Application (Auth/, Recommendation/)
  Services/<Area>/<Area>Module.cs Add<Area>Infrastructure(configuration) (§12)
  DependencyInjection.cs          AddInfrastructure(configuration)

ANGI.WebApi/
  Common/Models/ApiResponse.cs    ApiResponse<T>
  Configs/                        <Concern>Config + <Concern>Settings (CORS, JWT, rate limit)
  Controllers/                    thin controllers only (§11)
  Middlewares/                    IMiddleware implementations
  DependencyInjection.cs          AddWebApi(configuration)
  Program.cs

ANGI.Test/                        mirrors the project folders: Application/, Infrastructure/, WebApi/, Domain/
```

## 2. Layers and dependencies

```
Domain  ←  Application  ←  Infrastructure
               ↑                 ↑
            WebApi  ─────────────┘ (DI registration only)
```

| Layer | Owns | Must never |
|---|---|---|
| Domain | Entities, enums, base classes | Reference another project or any NuGet package |
| Application | Use cases, DTOs, interfaces, validators, exceptions | Reference EF Core, ASP.NET Core, HTTP or SQL types |
| Infrastructure | `ANGIContext`, repositories, external service clients | Contain business rules |
| WebApi | HTTP pipeline, controllers, middlewares | Inject `ANGIContext`, a repository or any Infrastructure type |

Controllers and middlewares use only interfaces from `ANGI.Application.Common.Interfaces`.

## 3. Naming

Microsoft C# conventions:

| Element | Convention | Example |
|---|---|---|
| Class, interface, enum, method, property | PascalCase | `LoginUseCase`, `ExecuteAsync`, `PasswordHash` |
| Local variable, parameter | camelCase | `loginRequest`, `userId` |
| Private field | `_camelCase` | `_unitOfWork` |
| Interface | `I` prefix | `ILoginUseCase` |
| Enum value | PascalCase | `UserStatus.PendingVerification` |
| Use case | `<Feature>UseCase`, method `ExecuteAsync` | `RefreshTokenUseCase` |
| Validator | `<RequestDto>Validator` | `LoginRequestDtoValidator` |
| Repository | `<Name>Repository` | `AuthenticationRepository` |
| Controller | `<PluralResource>Controller`; `AuthenticationController` for `/api/v1/auth` | `RoadmapsController` |

### DTO names from the API Design

Every DTO ends in `Dto` (many API Design names are also entity names: `Review`, `Tag`, `RoadmapItem`).

| In the API Design | C# name | Example |
|---|---|---|
| Object in sheet "DTO" | `<Name>Dto` | `DishCard` → `DishCardDto`, `AuthResult` → `AuthResultDto` |
| Request body or query string | `<Verb><Resource>RequestDto` | AUTH-04 → `LoginRequestDto`, DISH-01 → `BrowseDishesRequestDto` (`[FromQuery]`) |
| Response `…X` (all fields of DTO X) | `XDto` | RM-01 returns `RoadmapDetailDto` |
| Response with its own fields | `<Verb><Resource>ResponseDto` | DISH-03 → `RollDishResponseDto` |
| `Paged<X>` | `Paged<XDto>` (`Application/Common/Models`) | `Paged<RestaurantCardDto>` |

- Property names are the API field names in PascalCase (`requestId` → `RequestId`); JSON is camelCase automatically.
- A shared DTO lives in `DTOs/<Module>/` of the module that owns its data (`DishCardDto` in `Discovery`); other modules may use it.

## 4. Adding a feature

Read the endpoint in the API Design and the tables in the Data Dictionary first. Then, in this order:

```
1.  Domain          entity or enum, if needed
2.  Infrastructure  IEntityTypeConfiguration in Persistences/Configs/, if the schema changes
3.  Infrastructure  one EF migration, after the configuration is complete (§16)
4.  Application     repository interface in Common/Interfaces/Repositories/<Module>/, if needed
5.  Application     DTOs in DTOs/<Module>/ (§3)
6.  Application     I<Feature>UseCase in Common/Interfaces/UseCases/<Module>/
7.  Application     validator in UseCases/Validators/<Module>/ (§6)
8.  Application     use case in UseCases/<Module>/<Feature>/
                      ├─ validate first (§6)
                      ├─ ICurrentUserService for the caller's identity (§13)
                      └─ IUnitOfWork for writes (§14)
9.  Application     register the use case in Add<Module>UseCases() (§12)
10. Infrastructure  repository implementation
11. Infrastructure  register the repository in the module's Add…Infrastructure() (§12)
12. WebApi          controller action (§11) with [Authorize] / [Authorize(Roles = "...")] as the API Design says
13. Test            unit tests for the use case and validator in ANGI.Test
```

## 5. Responses

Every HTTP response, success or error, is `ApiResponse<T>` (sheet "Tổng quan" → "Định dạng response" and sheet "DTO" of the API Design). The fields listed for an endpoint are the content of `Data`.

```csharp
public class ApiResponse<T>
{
    public bool Success { get; set; }
    public string? Message { get; set; }      // user-facing message, usually null on success
    public string? ErrorCode { get; set; }    // null on success; on error a code from sheet "Mã lỗi"
    public T? Data { get; set; }              // null on error or when the endpoint returns nothing

    [JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]
    public Dictionary<string, string[]>? Errors { get; set; }  // only VALIDATION_FAILED: field → messages
}
```

JSON: `{ "success": true, "message": null, "errorCode": null, "data": { ... } }`. The internal Reco API is the only exception: it is not wrapped (`project_architecture.md` §8).

| Operation | Status | Body |
|---|---|---|
| Read, update | 200 OK | `Success = true`, `Data = dto` |
| Create | 201 Created | `Success = true`, `Data = dto` |
| Delete or nothing to return (logout, resend email, change password) | 200 OK | `Success = true`, `Data = null` |
| Background job accepted (RM-10, IMP-01 only) | 202 Accepted | `Success = true`, `Data = dto` |

- Use exactly the status the API Design gives the endpoint. Never return 204 or `NoContent()`.
- Responses produced outside the exception middleware use the same shape:

| Case | Configured in | Status / ErrorCode |
|---|---|---|
| Missing or invalid token | `JwtBearerEvents.OnChallenge` | 401 `UNAUTHORIZED` |
| Wrong role or missing permission | `JwtBearerEvents.OnForbidden` or an `IAuthorizationMiddlewareResultHandler` | 403 `FORBIDDEN` |
| Model binding fails (bad JSON, wrong type) | `ApiBehaviorOptions.InvalidModelStateResponseFactory` | 400 `VALIDATION_FAILED` + `Errors` |
| Rate limit exceeded | `RateLimiterOptions.OnRejected`, with `Retry-After` | 429 `TOO_MANY_REQUESTS` |

- Never write a raw JSON error, and never set the status code without the body or the body without the status code.

## 6. Validation

- Only FluentValidation; no DataAnnotations on DTOs.
- One validator per request DTO in `Application/UseCases/Validators/<Module>/`; `AddValidatorsFromAssembly()` registers them.
- The first statement of `ExecuteAsync` is `await _validator.ValidateAndThrowAsync(request, ct);`.
- Validate every value the database cannot catch. A non-nullable `int` / `decimal` defaults to 0, so a required number (restaurant `Latitude` / `Longitude`) needs an explicit rule; NOT NULL does not stop 0.

## 7. Mapping

- Entity → DTO mapping happens in Application: in the use case, or in a `<Name>Mapper` of the module when several use cases share it. Never in a controller.
- A repository that uses `Include()` returns entities; the use case maps them.
- A repository that uses `Select()` may project straight into the DTO; do not map that result again.
- Enum values in DTOs are the snake_case values of sheet "Enum" (`pending_verification`), never the C# names.

## 8. Errors

```
Controller → use case / service → throw an AppException subclass → ExceptionHandlingMiddleware → ApiResponse
```

- Every expected error is thrown as an exception that inherits `AppException` and carries an `ErrorCode`. Controllers never catch exceptions to build responses.
- Error codes and their HTTP status come only from the API Design: sheet "Mã lỗi", and column "Mã lỗi riêng" of sheet "Backend API" for the endpoint. Never invent a code (§0 of `project_architecture.md`).
- `Message` is shown to the user: write it in Vietnamese. Clients branch on `ErrorCode`, never on `Message`.
- An error that must return data (e.g. `ACCOUNT_SUSPENDED` with `suspendedUntil`) is a subclass of the matching exception (`AccountSuspendedException : ForbiddenException`) with its own case in `ExceptionHandlingMiddleware`, which puts the data DTO in `Data`.

```csharp
throw new BadRequestException("TOKEN_EXPIRED", "Liên kết đã hết hạn.");
throw new NotFoundException("RESTAURANT_NOT_FOUND", "Không tìm thấy nhà hàng.");
throw new ConflictException("REVIEW_ALREADY_EXISTS", "Bạn đã đánh giá nhà hàng này.");
```

`ExceptionHandlingMiddleware` maps:

```
ValidationException          → 400  VALIDATION_FAILED, Errors grouped by property (camelCase)
BadRequestException          → 400  ErrorCode from the exception
UnauthorizedException        → 401  ErrorCode from the exception
ForbiddenException           → 403  ErrorCode from the exception
NotFoundException            → 404  ErrorCode from the exception
ConflictException            → 409  ErrorCode from the exception
ServiceUnavailableException  → 503  ErrorCode from the exception
any other Exception          → 500  INTERNAL_ERROR, generic message; log the exception, never return its details
```

The API Design has no 410, 413, 415, 422 or 204: data and business-rule errors (expired token, file too large, wrong file type) are `BadRequestException` with their own `ErrorCode`.

## 9. Queries

- Lazy loading is forbidden. Load navigations with explicit `Include()` / `ThenInclude()`.
- `AsNoTracking()` on every read-only query.
- Use `Select()` to load only the needed columns; never load a full entity for a few fields. Do not combine `Include()` with `Select()`: the projection already joins.
- Use `Include()` only when the use case maps the full entity graph. With several collection includes add `AsSplitQuery()` (it has no effect on `Select()`).

```csharp
var cards = await _ctx.Dishes
    .AsNoTracking()
    .Where(d => d.Status == DishStatus.Active && d.IsAvailable)
    .Select(d => new DishCardDto { Id = d.Id, Name = d.Name, Price = d.Price, RestaurantName = d.Restaurant.Name })
    .ToListAsync(ct);

var restaurant = await _ctx.Restaurants
    .AsNoTracking()
    .Include(r => r.Images)
    .Include(r => r.BusinessHours)
    .AsSplitQuery()
    .FirstOrDefaultAsync(r => r.Id == id, ct);
```

## 10. Async and time

- Every method that does I/O (database, HTTP, file) is `async` and returns `Task` / `Task<T>`.
- Every async method takes a `CancellationToken` and passes it down from the controller to EF Core and `HttpClient`.
- Never `.Result`, `.Wait()` or `async void` (event handlers excepted). Never `SaveChanges()`; use `SaveChangesAsync(ct)`.
- Get the current time from the injected `TimeProvider` (`GetUtcNow()`), so tests can control it. Store and compare UTC only; never `DateTime.Now`.

## 11. Controllers

Controllers receive the request, call one use case, and return `ApiResponse<T>` with the status from §5. Nothing else: no business logic, no mapping, no try/catch, no repositories or `ANGIContext`.

```csharp
[ApiController]
[Route("api/v1/roadmaps")]
[Authorize(Roles = "TRAVELER")]
public class RoadmapsController : ControllerBase
{
    private readonly ICreateRoadmapUseCase _createRoadmap;

    public RoadmapsController(ICreateRoadmapUseCase createRoadmap) => _createRoadmap = createRoadmap;

    // RM-01
    [HttpPost]
    public async Task<IActionResult> Create(CreateRoadmapRequestDto request, CancellationToken ct)
    {
        var result = await _createRoadmap.ExecuteAsync(request, ct);
        return StatusCode(StatusCodes.Status201Created, new ApiResponse<RoadmapDetailDto> { Success = true, Data = result });
    }
}
```

Put the API Design endpoint id (`// RM-01`) above each action.

## 12. Dependency injection

- `Program.cs` calls only `AddApplication()`, `AddInfrastructure(configuration)`, `AddWebApi(configuration)`; adding a module never changes it.
- Each module registers its types in one extension method in each layer, called by one line from that layer's `DependencyInjection.cs`:
  - Application: `UseCases/<Module>/<Module>Module.cs` → `Add<Module>UseCases()`
  - Infrastructure: `Services/<Area>/<Area>Module.cs` → `Add<Area>Infrastructure(configuration)` (its repositories, services, settings and HTTP clients)
- A service used by several modules (e.g. `IRecommendationService`) gets its own area module, not a slot in another module's registration.
- Lifetimes: `AddScoped` for use cases, repositories and services; `AddSingleton` only for stateless utilities (`TimeProvider`); typed `AddHttpClient` for HTTP services.
- Never register Infrastructure types from Application.
- Settings classes bind a configuration section (`SectionName` constant) with `AddOptions<T>().Bind(...)`.
- Middlewares implement `IMiddleware` and are registered `AddScoped`. Order: `project_architecture.md` §4; `ExceptionHandlingMiddleware` stays first.

## 13. Current user

A use case that needs the caller's identity (author, ownership check) uses `ICurrentUserService`. Never inject `IHttpContextAccessor` into Application.

## 14. Transactions

- Every write goes through `IUnitOfWork`; repositories never expose `SaveChangesAsync`.
- Call `_unitOfWork.SaveChangesAsync(ct)` once, at the end of the use case.
- When reads and writes must be atomic together (e.g. rotating a refresh token), use `await using var transaction = await _unitOfWork.BeginTransactionAsync(ct);` and `await transaction.CommitAsync(ct)` after `SaveChangesAsync`. Disposing without commit rolls back.
- Transactions are controlled in the use case only, never in a controller or repository.

## 15. Entities and columns

| Topic | Rule |
|---|---|
| Columns | Exactly as the Data Dictionary (name, type, length, nullability, default). snake_case names are generated by `EFCore.NamingConventions`; never set a column name by hand |
| Configuration | One `IEntityTypeConfiguration<T>` per table in `Persistences/Configs/`; `ANGIContext` uses `ApplyConfigurationsFromAssembly` |
| Keys | Identity: `int` for `users`, `dishes`; `short` for `roles`, `permissions`, `tags`; `long` for every other table |
| Time | `DateTime` in UTC → `timestamptz` |
| Enums | `varchar` + `CHECK`. Never call `HasConversion`: `ApplyEnumConventions` stores the snake_case value of sheet "Enum" and generates the CHECK. Configure only `HasMaxLength` and, if the column has one, `HasDefaultValue`. `OutboxEventType` is stored UPPER_CASE, `FeedbackValue` as smallint 1 / -1 |
| Status checks | Compare with enum values (`dish.Status == DishStatus.Active`), never strings |
| Email | `citext` |
| Location | `decimal` → `numeric(9,6)`, required on `restaurants`. "Nearby" = bounding box, then Haversine; no PostGIS |
| JSON | `jsonb` columns are `string` properties |

```csharp
public abstract class BaseEntity<TKey> { public TKey Id { get; set; } = default!; }
public interface IHasCreatedAt { DateTime CreatedAt { get; set; } }
public interface IHasUpdatedAt { DateTime UpdatedAt { get; set; } }
public interface ISoftDelete    { DateTime? DeletedAt { get; set; } }
```

- An entity implements only the interfaces for the columns its table has. Composite-key tables and `review_replies` (key `review_id`) do not inherit `BaseEntity`.
- `CreatedAt` / `UpdatedAt` are set by `ANGIContext.SaveChangesAsync`; never set them in a use case.
- Soft delete (users, restaurants, roadmaps, blogs, blog_comments): set `DeletedAt` to the current UTC time, never call `Remove()`. A global filter hides deleted rows (`IgnoreQueryFilters()` to include them); a required navigation to a deleted row loads as `null`. Unique indexes skip deleted rows: `HasFilter("deleted_at IS NULL")`.
- Foreign keys are `Restrict` unless the configuration sets `Cascade` for owned child rows (images, business hours, dish tags, menu items, roadmap days and items, sessions and tokens). `roadmap_item_id` in `dish_feedbacks` and `restaurant_reviews` is `SetNull`.
- A constant database default (`dish_form = 'other'`, `is_available = true`) is repeated as the C# property initializer, because EF always sends the value.
- Never map or query schema `recommendation`.

## 16. Migrations

```bash
dotnet ef migrations add <Name> -p ANGI.Infrastructure -s ANGI.WebApi -o Persistences/Migrations
dotnet ef migrations has-pending-model-changes -p ANGI.Infrastructure -s ANGI.WebApi
```

- Schema `core` changes only through EF migrations; never run SQL by hand against a shared database.
- Pull `dev` immediately before `migrations add`. At most one migration per pull request, PascalCase name (`AddRestaurantTags`).
- Never edit `ANGIContextModelSnapshot.cs` by hand. Do not edit generated migration code, except to remove an EF-generated default that would hide missing data (comment why).
- CHECKs use `HasCheckConstraint`, extensions `HasPostgresExtension`. Only what EF cannot express goes into `migrationBuilder.Sql(...)` (triggers, sequence fixes after seeding).
- Adding or renaming an enum value changes its CHECK, so it needs a migration.
- Development applies pending migrations at startup and refuses to start when the model has changes without a migration; other environments migrate as a deploy step.
- If the migration conflicts with `dev`: delete your migration, pull `dev`, create it again.
